# Building the Dataset (book chapter 4)

From the O'Reilly companion repo (MIT). Nothing else in this pack covers where
examples come from. The optimizer results in `dspy-book-optimizers` all depend
on the dataset built here.

## Conversion is where types get fixed

One `convert` function per source. `.with_inputs()` names **only** what the
program receives; everything else is gold. Coerce types and map labels at
conversion time, never inside the metric.

```python
# HuggingFace, two inputs, first gold answer only
def convert(ex):
    return dspy.Example(question=ex['question'], context=ex['context'],
                        answer=ex['answers']['text'][0]).with_inputs('question', 'context')

# integer label -> string, at conversion time
label_map = {0: "negative", 1: "neutral", 2: "positive"}
dspy.Example(text=ex['text'], sentiment=label_map[ex['label']]).with_inputs('text')

# CSV
dspy.Example(text=row['text'], is_disaster=bool(row['target'])).with_inputs('text')
```

Getting `with_inputs` wrong is the quiet failure: a field left out is
unavailable to the program, and a gold field left in leaks the answer.

## Stratify by difficulty, not at random

The chapter's error-analysis notebook builds the set in three named tiers, a
few examples each, so *"each pattern from the error analysis is represented"*:

| Tier | Purpose |
|---|---|
| clear | the baseline should already get these right |
| boundary | the baseline might fail |
| ambiguous | hard for any model |

Genuinely ambiguous cases are **not** fixed. They go to a separate log with a
conservative default and a reason, because *"they tell you where the task
definition itself is incomplete."* That is a specification finding, not a model
failure, and treating it as a model failure is how you overfit to noise.

## Error notes are the feedback channel

Each error gets annotated with what the model predicted, what was correct, and
**why it went wrong as a mechanism** — for example, "model sees 'can't find'
and assumes a technical issue, but this is an account management question."

Those notes are not documentation. They are passed straight through to the
optimizer as the feedback string, so a GEPA-compatible metric can hand the
reflection model a human's diagnosis rather than a bare zero.

## Splits and sizes the chapter states

```python
random.Random(2024).shuffle(all_examples)      # seeded, or nothing reproduces
train_size, val_size = int(0.5 * n), int(0.25 * n)
```

50 / 25 / 25 for a hand-built set. For a large public corpus: 200 training
examples, 100 held-out validation while the optimizer searches, and 500
reserved for final evaluation — with validation and test drawn from **disjoint
index ranges** of the same split.

## Synthesizing data

Two patterns, with very different risk.

**Generation** produces a batch in one call:

```python
class FactGeneration(dspy.Signature):
    """Generate facts and their veracity."""
    sindex: str = dspy.InputField(desc="a random string seed")
    fact: str = dspy.OutputField()
    veracity: bool = dspy.OutputField()

generator = dspy.Predict(FactGeneration, n=15)
```

The only diversity guard is the random-seed input field plus temperature.
**There is no quality filter, no validation pass and no anti-collapse check in
the chapter.** Synthetic data generated by the model you are about to optimize
will carry that model's biases into its own training set. Add a filter.

Also: `n=15` is not honoured by every endpoint. DSPy can silently return fewer
completions and `zip` will truncate. Assert the length.

**Enrichment** is the safer pattern and the chapter's strongest anti-collapse
move: when you have real outputs but not the inputs your signature needs, write
the inverse signature and run it over the corpus. A real joke with a
synthesized topic is far better training data than a synthesized joke.

## PII

Rewrite each record to preserve structure while swapping in fake details, and
**carry the gold label across unchanged** so signal survives.

Three caveats the notebook does not state: the real PII is still sent to the
model provider; nothing verifies that the synthetic output actually dropped the
original identifiers; and nothing checks that the model did not echo a real
name. Add a diff or regex check before trusting it.

## What the chapter does not warn you about

There is **no** warning anywhere in chapter 4 about leakage, train/test
contamination or devset overfitting. Worse, chapter 3 evaluates on the full
dataset including the training rows, and one notebook optimizes against a slice
of its own test set. Do not inherit that. Supply these rules yourself:

- Validation and test never overlap, and neither overlaps train.
- The test set is touched once, at the end.
- Repeated optimization against one devset stops measuring quality.

## Anti-patterns

- An unseeded shuffle. The split changes every run and no result is comparable.
- Coercing types inside the metric instead of at conversion.
- Treating an ambiguous case as a model error; it is an underspecified task.
- Trusting synthetic data with no filter, especially from the model being optimized.
- `n=15` without asserting how many completions came back.
- Evaluating on data the optimizer saw.
- Discarding error notes; they are the feedback an optimizer needs.
